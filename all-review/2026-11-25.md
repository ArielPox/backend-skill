## 逐题批改

### 第 1 题

**原题：** 设备按 `created_at DESC, id DESC` 排序，第一页后插入一条排在最前的新设备。第二页继续用 `OFFSET` 可能出现什么现象？稳定排序解决了什么，仍未解决什么？

**你的回答：** 出现取错设备的状况，稳定排序保证了插入之后有序性，但是依然不能解决的offset会取错数。

**批改结果：3/5。** 你指出新插入会影响 OFFSET 翻页，也知道稳定排序无法消除这个影响。需要更准确地描述为跨页重复或遗漏，而非数据本身取错。

**正确答案：** `created_at DESC, id DESC` 在固定数据集上提供确定顺序。若第一页后插入排在最前的新设备，第二页的偏移位置会后移，可能再次读到第一页末尾的设备。稳定排序解决同时间戳记录顺序不确定的问题，不能保证多次请求看到同一份数据。需要跨页稳定遍历时，可考虑按排序键进行游标分页，并明确数据更新时的业务口径。

**解释：** OFFSET 每次按当前数据集的位置跳过记录，新记录会改变后续记录的位置。

### 第 2 题

**原题：** 项目导入接口返回 409 后，查库发现该项目仍存在但设备列表为空。这个证据指向哪一种事务边界错误？如何调整提交位置并复验？

**你的回答：** 说明有事务发生冲突，设备接入失败，现在需要做三个步骤的：1.查询当前项目id,2.回滚失败的seesion，3.查询当前项目下面是不是有设备，无设备只之后再重新提起提交，提交之后再查询当前项目以及设备清单。

**批改结果：1/5。** 你提出了查库和处理失败 Session，但未识别项目已经提前提交。对失败 Session 执行 rollback 不能撤销之前已提交的项目。

**正确答案：** 空项目说明项目创建在设备写入前被单独 `commit()`，破坏了整批原子性。应把创建项目、`flush()` 取得 ID、创建设备放在同一事务，只在全部成功后提交一次。设备编码冲突时回滚整个未提交事务。修复现有空项目要按业务规则清理或复用，再用新的项目编码重现冲突，确认项目和设备查询均为零行；修正输入重试后，确认项目与设备一起出现。

**解释：** `flush()` 不等于提交。已提交的项目无法靠后续 `rollback()` 撤销。

### 第 3 题

**原题：** 准备删除已经回填的 `last_seen_at` 列以回退迁移。为什么仅确认 Alembic 的 `downgrade` 能运行还不足够？

**你的回答：** 因为能运行代表撤销成功，数据库里面可能还有没有删除的脏数据的，需要查询脏数据是不是从库里面删除。

**批改结果：0/5。** 题目的主要风险是已回填的真实时间随列删除而丢失，目标是保护数据。

**正确答案：** `downgrade()` 能执行只证明结构操作可以完成。删除 `last_seen_at` 列会删除其中已经回填的数据。回退前要判断旧应用是否可兼容当前新表结构，能否只回退应用；若必须降级数据库，应先备份、验证恢复方式和数据丢失范围，在隔离环境演练，再核对关键行与字段。

**解释：** 迁移版本回退与业务数据恢复是不同动作，删列后的时间值不会由 Alembic 自动保留。

### 第 4 题

**原题：** 在 SSH 终端手动运行成功，systemd 服务日志却显示缺少 `DATABASE_URL`。不打印密码的前提下，你会检查 service 文件中的哪些配置及生效步骤？

**你的回答：** 这个不清楚的。

**批改结果：0/5，按没有头绪处理。**

**正确答案：** 检查 service 的 `[Service]` 中是否配置 `EnvironmentFile=/etc/myapp/app.env` 或对应的 `Environment=`，路径是否正确；环境文件应按 `DATABASE_URL=...` 写入，不加 `export`，并限制读取权限。修改 service 后执行 `systemctl daemon-reload`，重启该服务，再看 `systemctl status` 与 `journalctl -u` 的错误。只核对变量是否存在及连接目标，不输出密码，最后调用需要数据库的业务接口验证。

**解题切入点：** 先问“是谁启动了应用”。SSH shell 的 `export` 只传给它的子进程，systemd 启动的服务从单元配置获得环境。

### 第 5 题

**原题：** 设备详情缓存存在。更新数据库后，接口继续返回旧设备信息。按 Cache-aside 流程，写入事务与缓存删除应该怎样排序？之后一次读取会走什么链路？

**你的回答：** 应该是先删除缓存后删库，删除之后还要核对删除是不是完全成功了，缓存中是不是还有脏缓存数据，数据库的删除是不是原子性成功的，二次的发起查询检查是不是还有旧设备数据。

**批改结果：0/5。** 题目是更新设备信息，答案把它理解成删除设备，并颠倒了数据库提交与缓存失效的顺序。

**正确答案：** 先更新 PostgreSQL 并提交事务，提交成功后删除该设备对应的 Redis 缓存键。随后一次详情请求先查 Redis，未命中后查询 PostgreSQL 的新值，按 TTL 回填缓存并返回；再请求可命中缓存中的新值。验收时核对数据库记录、Redis 键、两次响应及命中或查库日志。

**解释：** 如果先删除   缓存而数据库事务尚未提交，另一个读请求可能读取旧数据并重新回填旧缓存。并发场景仍需考虑提交前开始的旧值回填竞态。
